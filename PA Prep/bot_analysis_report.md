# Technical Report: Bot Framework and Python Client Implementation

This report provides a detailed analysis of the bot framework and Python client implementation within the 2D optimization platform, intended for inclusion in Chapter 5.3 of the scientific thesis.

## 1. Bot/Client Technology Stack
- **Language:** Python 3.x (Uses `from __future__ import annotations` and type hinting).
- **Main Libraries:** 
    - `requests`: Used for all synchronous HTTP communication with the backend.
    - `math`: Standard library used for local RPN-based function evaluation.
    - `random` & `time`: Used for optimization algorithms and timing synchronization.
- **HTTP Communication:** REST-based interaction using the `requests` library.
- **Local Evaluation:** Custom RPN (Reverse Polish Notation) interpreter implemented in pure Python/math. No heavy external dependencies (like NumPy or SciPy) are required for the base client, ensuring high portability for student environments.
- **Configuration:** Bots are configured via Python variables in the script headers (e.g., `API_URL`, `SESSION_CODE`, `BOT_NAME`).

- **`student_bot_template.py`**: A documented starting point for students, implementing a simple Hill Climbing strategy using local evaluation.
- **`genetic_algorithm_template.py`**: A complex bot implementation demonstrating population-based optimization and batch synchronization.

## 3. Bot-Client API and Usage
The bot client is designed to be instantiated with a server URL and a session code.

**Key Exposed Methods:**
- `join(name, is_bot=True)`: Registers the bot in the session and retrieves the `blackbox` RPN payload.
- `evaluate_local(x, y)`: Computes the function value $z$ without network overhead using the RPN payload.
- `sync_trajectory(points)`: Submits a list of `{"x": x, "y": y, "z": z}` dictionaries to the server in a single batch.
- `get_public_info()`: Fetches session metadata like `max_steps` and `status`.

**Usage Example:**
```python
client = BlackBoxClient("http://localhost:8000", "ABC123")
client.join("MyBot")
z = client.evaluate_local(1.5, -2.0)
client.sync_trajectory([{"x": 1.5, "y": -2.0, "z": z}])
```

## 4. RPN Interpreter Implementation
The RPN interpreter is implemented in `BlackBoxClient.evaluate_local`. It uses a stack-based approach to process the `blackbox_payload` (a list of integers and floats).

- **Supported Operators:**
    - Variable injection: `OP_X` (1), `OP_Y` (2)
    - Constants: `OP_CONST` (3) followed by the value.
    - Arithmetic: `+` (10), `-` (11), `*` (12), `/` (13), `^` (14)
    - Functions: `sin` (15), `cos` (16), `sqrt` (17), `abs` (18), `exp` (19)
    - Constants: `PI` (20)
- **Mechanism:** The interpreter iterates through the bytecode. Constants and variables ($x, y$) are pushed onto the stack. Operators pop the required operands, perform the operation via the `math` library, and push the result back.
- **Limitations:** The interpreter assumes a valid RPN sequence generated by the backend. It does not currently handle complex numbers or domain errors (e.g., `sqrt(-1)`) explicitly beyond standard Python exceptions.

## 5. Implemented Bot Strategies

### Strategy: Genetic Algorithm (GA)
- **File:** `bot/genetic_algorithm_template.py`
- **Algorithm:** Population-based evolutionary search.
- **Parameters:** `POPULATION_SIZE` (500), `GENERATIONS` (1000), `MUTATION_RATE` (0.2).
- **Candidate Selection:** Tournament selection ($k=5$).
- **Local Evaluation:** Uses `evaluate_local` for all fitness calculations (up to 500,000 evaluations).
- **Data Submission:** Collects full trajectory and syncs in 20 chunks (every `max_steps // 20`).
- **Strengths:** Excellent for complex, non-convex landscapes; demonstrates high-volume local evaluation.

### Strategy: Hill Climbing (Local Search)
- **File:** `bot/student_bot_template.py`
- **Algorithm:** Greedy local search with step-size reduction.
- **Parameters:** `step_size` (initial 0.1), `max_local_steps`.
- **Candidate Selection:** Checks 4 orthogonal neighbors ($\pm \Delta x, \pm \Delta y$).
- **Local Evaluation:** Used to decide whether to move to a neighbor.
- **Data Submission:** Synchronizes every 50 points.
- **Strengths:** Simple to understand; low computational overhead; good for teaching the basics of optimization.

## 6. Bot Workflow
1. **Initialization:** User provides `API_URL` and `SESSION_CODE`.
2. **Join:** `POST /join` returns `participant_id`, `bounds`, and the `blackbox` RPN payload.
3. **Execution Loop:**
    - Bot generates candidate points $(x, y)$ based on its strategy.
    - Bot calls `evaluate_local(x, y)` to get $z$.
    - Bot tracks the best found solution and stores the point in a local list (`trajectory`).
4. **Synchronization:** When a threshold (e.g., 50 points or a generation end) is reached, the bot calls `sync_trajectory`.
5. **Termination:** The loop continues until `max_steps` is reached or the server reports the session as `revealed`.

## 7. Batch Synchronization
Batch synchronization is implemented via the `sync_trajectory` method.
- **Frequency:** Strategy-dependent (e.g., every 50 points or every 25,000 evaluations in GA).
- **Data per Point:** `x`, `y`, `z` (floats).
- **Ordering:** Implicitly handled by the list order; the backend stores them with a timestamp.
- **Network Load Reduction:** By sending 50 or 1000 points in a single POST request, the bot avoids the latency of individual HTTP handshakes. This allows for optimization speeds of $>10,000$ evals/sec without saturating the network or backend.

## 8. Integration with Backend and Frontend
- **Endpoints:** `/join`, `/sync_trajectory`, `/public`.
- **Visibility:** Submitted trajectories are stored in the PostgreSQL database. The frontend fetches these via the `/snapshot` or `/leaderboard` endpoints.
- **Representation:** Bots are identified as participants with the `is_bot=True` flag, allowing the frontend to filter or highlight them.
- **Communication:** The bot uses standard REST (REST only, no WebSockets) to ensure simplicity and compatibility with restricted student environments.

## 9. Error Handling and Robustness
- **Invalid Session:** `requests.raise_for_status()` catches 404/403 errors on join.
- **RPN Safety:** The interpreter throws a `ValueError` on unknown opcodes.
- **Out-of-Bounds:** Templates include logic to clip candidates to the `bounds` received during `join`.
- **Session End:** Bots are encouraged to check `get_public_info` periodically, though the `evaluate` endpoint (server-side) would return an error if the limit is exceeded.

## 12. Thesis-Relevant Interpretation
The bot framework's most critical feature for Chapter 5.3 is the **decoupling of evaluation from communication**.
- **Requirement F8 (Local Evaluation):** Successfully met by the RPN interpreter, allowing students to run complex algorithms without being throttled by network latency.
- **Requirement NF4 (Scalability):** The batch sync mechanism ensures the backend can handle tens of thousands of data points from multiple bots simultaneously without performance degradation.
- **Didactic Value:** Students can compare a simple Hill Climber (greedy) against a GA (stochastic/evolutionary) on the same "black box" function, observing real-time differences in exploration vs. exploitation patterns on the frontend map.
- **Phase 2 Evolution:** This implementation represents the transition from the simple Phase 1 (one-request-per-click) to a scalable research-grade optimization framework.

**Conclusion:** The Python client provides a robust, low-dependency gateway for students to engage with 2D optimization, balancing educational simplicity with professional-grade performance through its RPN-based local evaluation.
